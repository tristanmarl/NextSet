# CLAUDE.md

NextSet is a Monkey C Connect IQ strength-training app for five-button Garmin watches on Connect IQ 3.4+ (67 products in `manifest.xml`, minimum API 3.4.0 since 0.5.0, for the fenix 6 Pro / 6S Pro / 6X Pro, FR945 LTE, Descent Mk2 / Mk2S and MARQ Gen 1, all 1.28 MB app memory), developed and device-tested on the Forerunner 965 (`fr965`). Guard any API above 3.4 with `has` (MIP watches such as the fr255 family and the fenix 6 have no `Graphics.getVectorFont`), and do not call `Long.compareTo` (missing on CIQ 3.4: Symbol Not Found at runtime; compare Longs with `<`, `>`, `==`, `!=`). The 128 KB CIQ 3.4 watches (fenix 6 / 6S, Enduro, FR55, Instinct 2) are too small (NextSet uses about 254 KB); `scripts/pack-devices.sh` packs the device files CI needs. All jungles use `resources/` (the former `private/resources` copy is gone). Liftosaur API usage is in `docs/LIFTOSAUR_API.md`; contributor and release steps are in `CONTRIBUTING.md`. `AGENTS.md` contains repository rules; this file records build commands and current architecture.

## Commands

Use Connect IQ SDK 9.2.0 with its `bin` directory on `PATH`. This SDK requires `-y` even for simulator and test builds.

```sh
KEY="$HOME/.garmin-keys/NextSetDeveloperKey.der"
mkdir -p bin

# Production app and simulator
monkeyc -f monkey.jungle -d fr965 -o bin/NextSet.prg -y "$KEY"
monkeydo bin/NextSet.prg fr965

# Unit tests (tests.jungle includes source and tests)
monkeyc --unit-test -f tests.jungle -d fr965 -o bin/NextSet-tests.prg -y "$KEY"
monkeydo bin/NextSet-tests.prg fr965 -t

# Or: build + run + summary check with a timeout; exits 0 only on "PASSED (passed=N, failed=0, errors=0)"
scripts/test.sh
```

`monkeyc -l 3` (strict typecheck) does not build clean yet (486 errors for fr965 and fr255s, almost all `Any` from untyped Dictionary reads passed to `Object?` parameters such as `Model.sameString`); the normal build is clean.

The runner has previously exited 1 after reporting all tests passed; inspect its PASS/FAIL summary and record the result in `docs/DEVICE_TESTS.md`. A build or simulator result is not a physical-watch result.

While iterating, build only `fr965` (454 px) and `fenix7s` (240 px, small screen); build `fr255s` (MIP, no vector fonts) and `fenix6xpro` (CIQ 3.4) once before committing. `TEST_DEVICE=fenix6xpro scripts/test.sh` runs the unit tests on a CIQ 3.4 watch. Every release also gets the local store `.iq` (`monkeyc -e -r -f monkey.jungle -o bin/release-X.Y.Z/NextSet-X.Y.Z.iq -y "$KEY"`). The demo build (`monkey.demo.jungle`) switches screens every 3 s for screenshots. After a release run `scripts/clean-bin.sh`: it keeps only the newest store `.iq`, `ciq-devices.zip` and device logs in `bin/`.

## Architecture

Liftosaur is the source of routines and progression. The watch talks directly to `https://www.liftosaur.com/api/v1` through `Communications.makeWebRequest`; there is no NAS HTTP transport.

- `LiftosaurLogic.parseDays` reads the Liftoscript headers: any line starting with a single `#` opens the next week, numbered by position (the text is free: `# Week 4 - Deload`, `# #29 Preparation - Week 1`, empty), `## Name` is a day (space and a non-blank name up to 64 bytes required). Days before any week header are an implicit week 1 (a `#` header after them is rejected). The result and the journal key `weeks` are Arrays of day-name Arrays (index 0 = week 1; up to `Model.MAX_PROGRAM_DAYS` = 160 days and `MAX_PROGRAM_WEEKS` = 104 in total); only the week `/workout/next` reports is synced; of a synced week over eight days the first eight sync and the rest count as skipped (`weekDayRows`). A journal written by an older version (phase `next` with a flat `days` list and no `weeks`) still works through `daysForWeek`. Every rejection that ends in `Err.ROUTINE_SYNC_INVALID_RESPONSE` records a short reason (`LiftosaurLogic.parseProblem`, `Catalog.lastProblem`, `Model.liftosaurWorkoutProblem` / `liftosaurEntryProblem` / `liftosaurSetProblem` return the text, the `valid…` functions are `problem == null`, `LiftosaurSync.reject`); it is saved in the storage key `diag.sync` (`LiftosaurLogic.saveSyncProblem`, cleared by a successful sync) and Settings → Diagnostics appends it as "Last sync: …". Strings are built only on failure. A day reply whose envelope is valid for the expected program/week/day/name (`Catalog.dayCoordinates`) but has no exercises, or exercises `Catalog.parseRoutine` rejects (no weight, over the set/exercise limits, mixed units, …), is skipped instead of failing the sync: the index advances without a routine id (`Store.validRoutineSync` allows `routineIds.size() <= index`), unsupported days add to the journal's `skipCount` / `skipNote`, the notice reads "Synced 3 days, 1 skipped", the note stays in `diag.sync`, and `Catalog.nextRoutineId` offers the next synced day when Liftosaur's next day was skipped. A reply for another program, week, day or day name still stops the sync. `Model.timedSet` (set timer and one rep) decides timed holds everywhere; a set timer with more reps (EMOM) is a weight/reps set: it shows and logs like one, uploads `reps` and `weight` without `setTimer`, and has no work-window clock (not yet confirmed by a real write).

Sync flow since 0.5.1 (`LiftosaurSync`): journal phase `first` (new; `/workout/next` is asked first) → `week` (programId and nextWeek/nextDay known, no program name) → `/programs/current` parsed with `LiftosaurLogic.parseDaysFor(text, weekWanted)` (validates and counts every header but keeps only that week's names; `parseDays(text)` = week 0 = all weeks) → `days` (at most 8 rows) → one `/workout/next` per day. The phases `program` and `next` (all weeks stored) are written only by older versions and still resume with the old code path. Each reply is handled in steps, none of which walks a heavy day twice (a real FR255 hit the watchdog in `validRoutine` inside the one callback that did everything): the web callback only checks the envelope (`Catalog.dayCoordinates`) and walks the raw reply once (`Catalog.checkReply`), keeping the reply for the timer (`_pendingReply`, `STAGE_PROJECT`); then on the 150 ms timer `stepProjectRoutine` (`Catalog.projectChecked`, drops the reply), `stepValidateAndCommitRoutine` (the single `Catalog.validRoutine`, then `Store.commitPairChecked`, which skips its own validation; a routine that fails is skipped like an unsupported day) and the journal commit that also sends the next request (`STAGE_JOURNAL`); `Catalog.parseRoutine` = project + `validRoutine` for everything else. `runPendingStep` (public) runs one step; `continueAsyncWork` is the timer target; `pendingSteps()` / `SessionController.pendingSyncSteps` / `runPendingSyncStep` let tests run the steps without a timer (tests call `syncSettle(controller)` after `handleApiResponse` of a sync reply). Per-set validators take the load type as a number once per exercise (`Model.loadKind`, `validPlanTargetKind`). The journal lives in `_journal` while a sync runs (reloaded only after a relaunch); the routine is always committed before the journal points past it, so a relaunch re-asks the same day. `pumpAsyncWork` does nothing while steps are staged. Before each sync request `enoughMemory` checks `System.getSystemStats().freeMemory` against `LiftosaurLogic.syncMemoryNeed(purpose)`; below it the sync stops with `Err.SYNC_LOW_MEMORY` and "Low memory: N KB free, M KB needed" in Diagnostics (it first calls `SessionController.releaseConfigCache`, which drops the loaded routines; they reload lazily, never mid-workout). `applyRoutineSync` also drops them, reads the old ids with `loadConfig(true)` (no routines) and checks the new routines one at a time. The sync timers are created on first use.

- `Catalog` validates `/workout/next` replies and projects each day immediately into compact cached routines, including per-set targets and warmups. Exercise add/replace choices come from the synced program.
- Per-set rest and AMRAP (0.5.1): `Catalog.parseRoutine` stores each working set's `timer` as `restSec` and `isAmrap == true` as `amrap` in its set target; `createSession` copies both onto the working-set slot (only when present). `SessionLogic.completeSet` rests for the logged slot's `restSec` (warmups default 60), else the exercise `restSec` (routines cached earlier have no per-set rest); a superset round rests for the slot that ended it. `UiFormat.repsText` shows an AMRAP set's reps as "3+" (set screen, Overview line, routine preview); prefill and the one-START logging are unchanged and upload is unchanged.
- `Model` validates API data and persisted records. Config schema v4 has per-routine storage; older config schemas reset to defaults and need a fresh routine sync.
- `SessionController` owns the workout session and config, and owns a `LiftosaurSync` (`source/LiftosaurSync.mc`) that holds routine sync, the upload queue, key storage/test and the API request plumbing. The controller forwards the UI calls and gives the sync class a narrow host surface (`errorCode`/`setErrorCode`, `hasActiveSession`, `hasPendingFinalization`, `syncConfig`, `routineIds`, `settleRoutineSync`, `applyRoutineSync`). Only one request is in flight. Sync uses a persisted journal and replaces the active routine snapshot after successful downloads. Stored/wire strings (job states, journal phases, request purposes, error codes) are constants in `module Liftosaur` (`source/Liftosaur.mc`); the values are persisted, never change them.
- `UploadLogic` converts completed local sets into a job. Upload starts a workout with its explicit program/week/day and start time, maps to the returned set IDs, posts completed sets, then finishes with `intervals: [[startTime, endTime]]` (without it Liftosaur recorded `duration: 2s`) and `notes` only for substitutions or extra warmups. Notes become a `//` line above the Liftosaur history record; liftosaur2garmin up to `dda3034` fails on any such line, so do not add routine notes. The persisted queue holds at most four workouts and retries across launches. The queue being full blocks a new workout.
- Upload of a job in state `start` first does a non-mutating `GET /workout/next` and only POSTs `/workout/start` if `UploadLogic.previewMaps` passes; a mismatch stores `lastError=program_changed` (Err.WORKOUT_UPLOAD_MAPPING), not `blocked`. `workout_already_active` triggers `GET /workout/current`, and a workout with our startTime is adopted. Home menu and Settings offer confirmed "Skip this upload" and "Clear upload queue". Sync fetches only the week `/workout/next` reports (program days parsed up to 48, eight per week), restarts on manual sync, and runs its pivot from a 150 ms one-shot timer (`continueAsyncWork`, public).
- `Err` (`source/ErrorCodes.mc`) holds every error code with its long text (`message`) and Home notice (`shortMessage`) in two switch functions. Add a code in all places there, not in the UI.
- `Store` uses two generations for persisted state and journals and validates each unchanged generation once per launch (cache dropped on commit/delete). `_revs` caches the revision of every generation seen or written in this launch (first read or write fills it; `commitPair` never reads the old envelopes back; a delete or failed write drops the domain, a damaged or newer-version record is never cached, `forgetRevisions` is for tests that write storage behind the store's back; `loadPair` reads only the newer generation when both revisions are known and the older one was already validated); preserve staged commits and retry safety when changing upload or sync state. The 30 s workout clock checkpoint writes only the small `ckpt` key (`[sessionId, time]`); recovery uses it when it is newer than the session's own `lastCheckpointAt` and not in the future.
- Crash breadcrumb (`source/Breadcrumb.mc`): out-of-memory, watchdog and null/type deaths cannot be caught, so heavy steps write storage key `crumb` = `[step, week, day, freeKB, launchSeq]` (Numbers only, no reads) with `Breadcrumb.enter` and clear it with `Breadcrumb.leave` (one `deleteValue`); both swallow storage errors. Step codes 1-12 are persisted, never renumber. Hooks (only these): `LiftosaurSync.handleApiResponse` wraps `handleApiResponseBody` (steps 1/2/3 program/next/day reply, 7/8/9 upload start/sets/finish via `Breadcrumb.enterForPurpose`), `runPendingStep` wraps `runPendingStepBody` (3 projection, 4 routine commit, 5 journal commit), `applyRoutineSync` in `advanceRoutineSync` (6), `Breadcrumb.at(week, day)` when a day request goes out (memory only), `SessionController.advanceFinalization` wraps `advanceFinalizationBody` (10) and the `saveRecording()` call (11); `NextSetApp.onStop` calls `leave`. Step 12 (history) is reserved, unused. Never add hooks to onTick, rest/alert code, the set-logging press or `updateDraft`. `NextSetApp.onStart` calls `Breadcrumb.onLaunch(versionCode)`: a left-over crumb moves to `crumb.last` (`[step, week, day, freeKB, launchSeq, version]`); a successful sync clears `crumb.last`. Diagnostics is `Breadcrumb.summary` ("NextSet <version> <partNumber> · Stopped in: day reply W1 D3, 38 KB free · Last sync: <reason>", each part only when present) followed by the timings.
- Rest expiry and the timed-set target alert change the session in memory and are saved ~2 s later by the draft timer, so no storage write runs in the same tick as the 1 s vibration and redraw (a firmware crash on 2026-10-29 came in that second; see `docs/DEVICE_TESTS.md`). Keep heavy work (commits, FIT laps, requests) out of the alert tick. `NextSetApp` owns timers and resumes pending work on launch.
- Warmups: each session exercise has optional `warmupSlots` (max 4, from the routine's warmups) addressed as slot `Model.WARMUP_BASE + i` (100+); use `Model.slotAt` and `SessionLogic.activeSlot` (warmups first, then working sets) rather than indexing `slots`. `nextSlot`, totals, prefill and superset rotation stay working-sets-only. Warmup FIT laps use lap field `set` = 0. Upload rows `warmups` map by position onto the start reply's `warmupSets`; extras go to `extraWarmups` (finish notes).
- Plain (weight/bodyweight) sets and warmups log in one START press (`completeDraft`); there is no set clock, and a `setRun` saved by 0.3.1 is ignored and dropped on load. FIT `active_s` is the measured duration for timed sets and 0 otherwise. A cancelled workout runs only the finalizing commit, the FIT discard and the tombstone commit (no history, last-performance or upload steps).
- UI hints are icons drawn with Dc primitives (`source/ui/Icons.mc`; button angles come from the fr965 simulator layout and live in one place). UP/DOWN draft edits go through `SessionController.updateDraft` into memory only; `flushDraft` (2 s timer, app stop) persists them and any other commit includes them. `commit` records the longest save time for Settings → Diagnostics. After a cancelled workout `Navigator.finalized` returns to Home with a notice instead of exiting.
- `StrengthRecorder` still records a Training / Generic FIT activity with per-set lap fields and session summary fields. The exercise lap field is 64 bytes; `fitText` cuts names at whole characters to fit. It is a Garmin activity fallback, not a native planned workout.
- Set screen input: keys act on press (0.3.4 behaviour). On the FR965 only hold UP (KEY_MENU) reaches an app; hold START, DOWN and LIGHT are firmware shortcuts (hold DOWN opens music controls), so do not use holds. UP/DOWN always change the reps (the duration of a timed set), START logs; there is no load focus on this screen (hold UP opens Change weight). BACK steps back in time (0.4.3): set screen → last logged set of this exercise in the two-level editor → Overview → Resume / Save / Discard. `ExerciseView.stepBack` pauses a running timed set of the exercise, then opens `SessionLogic.lastLoggedSlot` (working sets; warmups only while no working set is logged) with `Navigator.setEdit(entryId, slot, true, false)`, or pops to the Overview when `EditorLogic.backOpensEditor` says nothing is logged. Hold UP is `ExerciseView.changeLoad` (`EditorLogic.holdUpAction`: weight / time / none; none = bodyweight, no hold-UP edge icon). There is no exercise menu any more (`WorkoutMenus.mc`, `ExerciseMenuDelegate`, Skip warmups, Skip rest, Add set item, Log paused set, Reopen exercise are gone; the controller functions `skipWarmups`, `restAction`, `closeExercise`, `completeTimed` stay). A paused timed set is resumed with START; Change time resets it. An exercise closed early by an older version is reopened by `Navigator.exercise` (Overview START calls `closeExercise(entryId, false)` before opening the set screen). START on a finished exercise opens its set screen with the green check (BACK still reaches its last set). `ExerciseDelegate` extends `KeyDelegate` with `_anyPressType = true` (the opt-in that dispatches START/UP/DOWN whatever the press type, like the former BehaviorDelegate) and keeps the `_armed` re-arm on `onKeyReleased` and the 800 ms `lastSetSavedAt` guard. `RapidPress` (`source/ui/SetEditView.mc`) speeds up fast same-direction presses in the editor (x2 from the 4th, x4 from the 8th).
- Set editor (buttons only): `SetEditView(entryId, slot, correcting, single)`. Fields per load type are in `EditorLogic.fields` (weight/assistance: `load100`, `reps`; bodyweight: `reps`; timed: `durationSec`). Hold UP on the set screen → **Change weight** (**Change time** for timed sets, which are paused and reset first; none for bodyweight) opens the one-field mode (`single`, `EditorLogic.singleField`): it starts in EDIT on that field, UP/DOWN change it (weight by the exercise's `weightIncrement100` with `RapidPress`), START saves (`updateDraft`) and closes, BACK closes without saving (`EditorLogic.startSaves` / `backSaves`). BACK on the set screen opens the last logged set in the two-level editor (`correcting`, `EditorLogic.MODE_SELECT` / `MODE_EDIT`), titled "Set N" / "Warmup N": SELECT shows a first row **Continue** (`EditorLogic.ROW_CONTINUE`, preselected, `isContinueRow`; medium text, green when selected, framed in white), the fields big (`UiFormat.drawBigFrom`) and a last row **Delete** (`EditorLogic.rows`, `isDeleteRow`, `fieldOffset` maps row index to field index; four rows use the MEDIUM number font at 41/55/69/83 %, three the LARGE one, so they fit the round fenix7s), the selected one framed in white, UP/DOWN move, START on Continue saves any change (`correctSet`) and pops only the editor, so BACK then START on the set screen just continues (0.4.6; edge icon `EditorLogic.startIcon`: play on Continue, check on other rows and in EDIT); START otherwise enters a field or, on Delete, pushes `ConfirmView("Delete set N?", "Keep", "Delete")` with `DeleteSetAction` (undoSet, pops confirmation and editor, so the set screen shows the set as open again; on failure the editor shows "Not deleted"); EDIT shows a field yellow and underlined, START keeps it, BACK restores the value from when it was entered; BACK in SELECT saves the changed fields (`correctSet`; nothing written when unchanged; a second BACK after a failed save leaves without saving) and `SetEditView.leave(false)` pops the editor and the set screen below it, landing on the Overview. `NumberEditView` remains for settings (rest, step) only. The one-time hint "Hold UP: change weight" (weight/assistance exercises) uses the storage key `hint.load`.
- Weight step is automatic (0.4.2): the Liftosaur data NextSet reads (`/workout/next` sets, `docs/LIFTOSAUR_API.md`) has no rounding or increment field, so `Catalog` uses `Model.defaultIncrement100` (2.5 kg = 250, 5 lb = 500) for new routines; a routine cached before 0.4.2 with the old kg default 100 is read as 250 in `createSession`. Stored `config.incrementOverrides` (by exercise name) are still read and applied after that, but nothing in the UI sets them any more.
- Input: every custom view delegate extends `KeyDelegate` (a `WatchUi.InputDelegate`, never a BehaviorDelegate): touch is consumed everywhere and the five keys go to `onStartKey`/`onBackKey`/`onUpKey`/`onDownKey`/`onMenuKey` (hold UP arrives as KEY_MENU). Only Garmin's own `Menu2` menus and the `TextPicker` still take touch. `FinishingWorkoutDelegate` retries a failed save with START or hold UP.
- Finish flow (key-only, no Menu2): BACK on the Overview and BACK on Home with an active workout, and the prompt after the last set or the last skipped exercise, call `Navigator.review()` directly (0.4.5). It pushes `FinishChoiceView` (`source/ui/FinishViews.mc`) even with no set logged: three choices Resume (selected first), Save, Discard in `FONT_MEDIUM` (selected yellow and underlined, others gray), a small caption with the workout time and sets (`UiFormat.reviewStats`). The pure rules are in `FinishLogic` (`source/FinishLogic.mc`: `label`, `move` wraps, `actionFor(selected, setsDone)`, `backAction`; unit-tested). UP/DOWN move, START acts (Resume pops; Save calls `requestWorkoutFinish("completed")`, with no set it only shows "Log a set before saving"; Discard pushes `ConfirmView("Discard workout?", "Keep", "Discard")` with `DiscardWorkoutAction`: Keep pops confirm and choice, i.e. back to the workout, Discard calls `requestWorkoutFinish("aborted")`, BACK on the confirm returns to the choice), BACK resumes. There is no menu, Workout… submenu or Cancel workout item; `ReviewView` is gone. `ConfirmView` draws its title with `UiFormat.drawTitle` like the review and its choices in `FONT_MEDIUM`. Delete set N (from the last-set editor) and the upload-queue / skip-upload / clear-key confirmations are the same `ConfirmView` with a `ConfirmAction` (`DeleteSetAction`, `QueueAction`). These delegates extend `KeyDelegate` (`source/ui/KeyDelegate.mc`, a `WatchUi.InputDelegate` that dispatches only physical keys to `onStartKey`/`onBackKey`/`onUpKey`/`onDownKey`/`onMenuKey` and consumes every touch callback; hold UP arrives as KEY_MENU; the Overview uses it for Add set: `OverviewView.addSet` → `SessionLogic.canAddSet` / `SessionController.addSet`, `buzz(false)`, error text in the bottom row, edge icon `Icons.addMarker`). START within 800 ms of a screen opening is ignored (`FinishGuard`), so the set-logging press cannot confirm the end-of-workout prompt. Settings and the routine/history menus stay Menu2 system UI.
- Summary sync (0.4.5): `SummaryView` shows "START: Sync to Liftosaur" (caption font, green, 89 %, falling back to "START: Sync" when the round screen is too narrow at that height) only while `SessionController.syncActionable()` (`LiftosaurLogic.syncActionable(state, uploading, hasKey)`: upload pending in the queue, not uploading, key set; unit-tested). `SummaryDelegate`: START opens the Garmin retry choice first when the activity is unresolved (that menu has a "Sync to Liftosaur" item too), else syncs now with `retryUploads()` while actionable, else exits (ignored while uploading); BACK exits (or opens the Garmin choice), never syncs. The status row already shows arrow / check / red error text live.
- Hold-UP icon kinds (`Icons.holdMarker`): "menu" dots (Home), "plus" (Overview), "weight" dumbbell and "time" clock (set screen, `Icons.loadMarker` from `EditorLogic.holdUpAction`).
- Rest ring: while a rest runs, `ExerciseView.drawRestRing` draws a dim ring at the very edge (outside the button icons; inside them it crossed the title) with a blue arc for the remaining fraction (`RestClock.ringFraction`, `ringEndDegrees`, unit-tested) and a full green ring in overtime. It adds no redraw beyond the existing 1 s rest redraw.
- Superset switch cue: `NextSetApp.buzz(true)` is a single-profile vibration plus a second one from a later `onTick` (`BuzzLogic`, `_buzzRepeatAt`), never in a tick that vibrates or whose checkpoint write is due (`SessionController.checkpointDue`). Multi-profile `Attention.vibrate` patterns did not vibrate at all on a real FR965 in the sibling app ColdStart 0.1.2, so do not use them.
- `source/ui/` contains button-operated views and delegates. `Navigator` owns screen transitions; its finish-flow functions are in `source/ui/WorkoutNavigator.mc` (same module), the finish views and delegates in `FinishViews.mc`. Keep callbacks passed to `method(:callback)` public; private timer or web callbacks can compile but fail at runtime.

Requests need the phone or watch Wi-Fi, so they must remain asynchronous and outside watchdog-sensitive work. A response that does not fit device memory should produce a recoverable error; convert large workout responses immediately and do not retain the raw response. The Liftoscript parser is capped at 16 KiB.

The Liftosaur key is entered on the watch (Settings → Liftosaur key, `TextPicker` via `NextSetApp.afterKeyEntry`) and stored only in watch app storage (`Store` domain `apikey`); there is no Connect IQ app setting. It is shown only masked, and Settings has Test key (`key_test`, read-only `GET /programs/current`) and Clear key. Never hard-code, print, commit, or place it in fixtures. It grants Liftosaur account access. Tests must use sanitized fixtures and fakes; do not make live POST requests unless the user explicitly approves the first real workout write.

RPE, prompted variables, one-sided timed sets, pounds, unilateral `repsLeft` and timed-set progression have not been verified by a real Liftosaur workout write. Keep these limitations visible until the approved device check confirms behavior.

- Screen layout (UI rules below): `UiFormat.drawTitle` (name, one line medium or two lines small), `Icons.setProgress` (always dots, one row: first one smaller gray dot per warmup, done filled gray, the up-next one filled white, open a gray outline; then one dot per working set, bigger, open sets with a light-gray thick outline, done green, the current one white with a ring; no "Warmup 1/2" text and no "4/8" counter; the order, states and sizes come from `DotsLogic.kinds` / `DotsLogic.layout`, which shrink the gap, then the dots, to the width `Icons.dotsWidth` allows between the screen chord and the hold-UP ring; a one-sided timed set shows "Left side" / "Right side" in a small line under the dots), `UiFormat.drawBig` (number font with small units, focus part yellow and underlined) and `UiFormat.drawHrRow` (live HR from `Activity.getActivityInfo()`, or an error in red) at fixed heights (25 / 39 / 57 / 79 %). The Overview uses the same rows (0.4.7): exercise name, the same `Icons.setProgress` dots row at 39 % for the shown exercise (its warmups and sets, current = `SessionLogic.activeSlot`, none when complete), "Exercise 2/8" (gray, `FONT_XTINY`, 51 %), the next set in `FONT_SMALL` at 64 % (`UiFormat.draftLine`, kg/lb aware, "Warmup " prefix, only while a set is open) and heart rate. `NextSetApp.onTick` redraws the set screen and Overview when the HR changes and keeps avg/max in memory for the summary. The one-time load hint is remembered in the storage key `hint.load`.
- Units: weights keep the account's unit (`Model.weightUnit`, exercise `loadUnit` / routine `unit` = "kg" or "lb"; load100 is hundredths of that unit). Jobs store `unit` per exercise (absent = kg) and upload with `UploadLogic.weightString`; FIT fields are converted with `Model.toKg`.
- Values Liftosaur asks for: plan targets keep `logRpe` / `rpe10`, exercises keep `prompts` and `userVars` (defaults = advertised values). `QuestionLogic.afterSet` decides what `QuestionView` asks after a set; answers go to completed `rpe10` and exercise `userVars`. One-sided timed sets store the left hold in the draft (`leftSec`) and complete with `durationLeftSec`. `UploadLogic.mappedCompleted` sends `rpe`, `userVars` and `setTimerLeft`, falling back to the program's suggestion.

## UI rules

Every screen change follows these rules; check fr965 (454 px) and fenix7s (240 px) in the simulator.

**Everything earns its place.** Screen space on a watch is tiny: an element stays only if the lifter needs it at that moment to decide what to do. When in doubt, leave it out or move it to a menu. Never shrink or cut text to make room: remove something instead.

1. **One glance, one question.** Each screen answers one question: the set screen "what do I lift", the rest screen "when do I go and with what", the summary "how did it go". Everything else lives in a menu.
2. **One meaning per colour.** Yellow = you are changing something (edit field, UP/DOWN arrows). Blue = resting (ring, rest time). Green = done or go (logged, rest over, uploaded). Red = something is wrong, and the heart. White = information. Gray = secondary text.
3. **Fixed positions.** Weight and reps, HR, and the set position sit in the same place on every workout screen.
4. **Fixed buttons.** START = the obvious next step, BACK = back and never destructive, UP/DOWN = change what is highlighted, hold UP = one shortcut (set screen: Change weight, Overview: Add set; there is no menu). No other holds.
5. **Undo over confirm.** Confirm only what cannot be undone (discard a workout, clear the upload queue, clear the key). Everything else is fixable afterwards (BACK to the last set: edit or Delete).
6. **Feel it without looking.** One single-profile vibration per event, told apart by length: set logged short, 10 s before rest end medium, rest over long.
7. **Show progress, don't describe it.** Dots for sets instead of "2/14 SETS"; icons (check, clock, cross) for status.
8. **Teach once.** No permanent button help in text: the edge icons show what each button does. A hint may show the first time a screen is used, then never again.
9. **Readable in the worst case.** Sweat, motion, sunlight, 240 px MIP: high contrast, big numbers for weight, reps and time, at most one small line per screen, no dark blue on black.
10. **One press per set.** Following the plan must stay one START per set; never add a step to that path.

Words appear only when something is wrong; success is an icon. One clock per screen: rest countdown during rest, total time only on the summary.

## Testing and evidence

Keep long boolean chains in tests split into named variables and sequential `check` calls: a single huge `&&` expression of mixed-type calls made the compiler run out of memory (`OutOfMemoryError` in the typechecker). Pure logic tests are free functions marked `(:test)` in `tests/*.mc`, accepting `Test.Logger` and returning `Boolean`; `check()` is in `WorkoutTests.mc`. Keep fixtures sanitized under `tests/resources/`. Simulator, physical FR965, and Garmin Connect evidence are recorded separately in `docs/DEVICE_TESTS.md`. Device status (what is confirmed and what is pending) is in `docs/DEVICE_TESTS.md`.

Fuzz tests (`tests/FuzzLogic.mc` module `Fuzz`, `tests/FuzzTests.mc`): a seeded LCG plus value/text mutators feed mutated Liftosaur replies, the program text and stored records to every outside-data parser; a case passes when nothing throws. Each case prints a breadcrumb `fz <label> seed=N | <mutations>` before its call: a *caught* exception is logged with its seed, but a fatal Monkey C error (a method called on a value of the wrong type, "Symbol Not Found", array out of bounds, "Failed invoking <symbol>") cannot be caught and aborts the test, so the last `fz` line before its stack trace names the seed. Findings: validators (`Model.valid*`, `Store` loads) must never throw on any input; consumers (`startBody`, `createSession`, `SessionLogic.*`) are only called on data a validator accepted, since callers guarantee that. Monkey C's call stack is only about a dozen frames deep (the mutators walk iteratively), `0.0f/0.0f` throws, and a started sync request leaves a running timer, so the sync/upload tests share one `SessionController`. Connect IQ 3.4 allows only 253 global members, so the fuzz helpers live in `module FuzzKit`. `monkeydo prg device -t testName` runs one test.

The old Garmin catalog and manual Upper/Lower routine editor have been removed. Do not regenerate or restore them; superseded plans are only in git history.
